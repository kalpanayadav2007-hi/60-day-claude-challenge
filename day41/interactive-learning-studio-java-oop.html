Foundations — Classes, Objects & Encapsulation

Foundational understanding · ~40 min

What is a Class? What is an Object?

A class is a blueprint. It doesn't exist as data in memory by itself — it describes what data (fields) and behavior (methods) any object built from it will have. An object is a concrete instance built from that blueprint, with its own actual values sitting in memory.

public class Car {
    private String brand;
    private int speed;

    public Car(String brand) {
        this.brand = brand;
        this.speed = 0;
    }

    public void accelerate(int amount) {
        speed += amount;
    }
}

// Using the blueprint to create real objects:
Car myCar = new Car("Tata");
Car yourCar = new Car("Mahindra");
myCar.accelerate(20);  // only myCar's speed changes
Analogy: Think of a class like the architectural blueprint for a house. The blueprint isn't a house you can live in — it's just a plan. Every actual house built from that blueprint (an object) has its own address, its own paint color, its own furniture, even though they share the same floor plan.

Diagram: Class vs. Instance

Encapsulation: Protecting the Data

Encapsulation means bundling data (fields) with the methods that operate on it, and restricting direct outside access using access modifiers like private. Instead of letting anyone change speed directly, you expose controlled methods (getters/setters) that enforce rules.

private int speed;

public void setSpeed(int newSpeed) {
    if (newSpeed >= 0 && newSpeed <= 220) {
        speed = newSpeed;
    }  // invalid values are silently rejected — data stays valid
}
Analogy: Encapsulation is like a car's dashboard. You press the accelerator pedal (a public method) — you don't reach under the hood and manually spin the engine's internals (a private field). The pedal enforces limits and safety checks that direct access would bypass.

Common Misconception: "A class and an object are basically the same thing." They are not — a class is never itself "used" in a running program; only objects (instances) hold real data and get manipulated. Confusing the two leads to code that tries to call instance methods without ever creating an object.

Key Takeaways

  • new creates a new object with its own copy of instance fields.
  • Encapsulation hides internal state behind private fields and controlled public methods.
  • Getters/setters let you validate or restrict how data changes.

Inheritance & Polymorphism

Applying foundations · ~45 min

Inheritance: Reusing a Blueprint

Inheritance lets one class (a subclass) acquire fields and methods from another (a superclass) using extends. It models an "is-a" relationship: a SportsCar is a Car, with everything a Car has, plus extras.

public class Vehicle {
    protected int speed = 0;
    public void accelerate(int amt) { speed += amt; }
}

public class SportsCar extends Vehicle {
    public void activateTurbo() {
        speed += 50;  // reuses inherited 'speed' field
    }
}
Analogy: Inheritance is like a family recipe passed down through generations. A grandchild's recipe (subclass) starts from the grandparent's base recipe (superclass) — same core technique — but can add or tweak steps without rewriting the whole thing from scratch.

Method Overriding & super

A subclass can override an inherited method to provide its own specific behavior, while still being able to call the original via super.

public class SportsCar extends Vehicle {
    @Override
    public void accelerate(int amt) {
        super.accelerate(amt * 2);  // sports cars accelerate faster
    }
}

Polymorphism: One Interface, Many Forms

Polymorphism lets you treat different subclasses through a common superclass reference, while each object still runs its own overridden behavior at runtime. This is runtime (dynamic) polymorphism.

Vehicle v1 = new Vehicle();
Vehicle v2 = new SportsCar();  // upcasting

v1.accelerate(10);  // speed += 10
v2.accelerate(10);  // speed += 20 — SportsCar's version runs
Analogy: Imagine pressing "play" on a universal remote. The button (interface) is the same for a TV, a projector, or a soundbar, but each device (subclass) responds to "play" in its own specific way. You don't need a different remote for each.

Common Misconception: "Overloading is a form of polymorphism just like overriding." Overloading (same method name, different parameters) is resolved at compile time — it's often called static/compile-time polymorphism, but it doesn't involve dynamic dispatch. True runtime polymorphism specifically comes from overriding through inheritance.

Practical Exercise

Create a Shape superclass with a method area() returning 0, and two subclasses Circle and Rectangle that override it correctly.

public class Shape {
    public double area() { return 0; }
}
public class Circle extends Shape {
    private double radius;
    public Circle(double r) { radius = r; }
    @Override
    public double area() { return Math.PI * radius * radius; }
}

Key Takeaways

  • extends creates an "is-a" relationship and reuses superclass code.
  • Overriding replaces inherited behavior; super can still call the original.
  • Polymorphism lets a superclass reference call subclass-specific behavior at runtime.
  • Overloading ≠ overriding — different mechanisms, resolved at different times.

Abstraction & Interfaces

Practical application · ~40 min

Abstract Classes: Partial Blueprints

An abstract class can declare methods without a body (abstract methods) and force subclasses to implement them, while still sharing common code. It cannot be instantiated directly.

public abstract class Employee {
    protected String name;
    public Employee(String name) { this.name = name; }

    public abstract double calculateSalary();  // no body — must be implemented

    public void printPayslip() {   // shared, concrete method
        System.out.println(name + ": ₹" + calculateSalary());
    }
}
Analogy: An abstract class is like a job description template with some fields already filled in (company name, HR policy) but a blank labeled "core responsibilities" that every specific role must fill in differently — a designer and an accountant both have "core responsibilities," just answered differently.

Interfaces: Pure Contracts

An interface defines a contract — a set of methods a class promises to implement — without providing implementation (traditionally). A class can implement multiple interfaces, which is Java's way around the lack of multiple class inheritance.

public interface Payable {
    double calculatePay();
}
public interface Reportable {
    void generateReport();
}

public class Contractor implements Payable, Reportable {
    @Override
    public double calculatePay() { return 50000; }
    @Override
    public void generateReport() { System.out.println("Report generated"); }
}
Analogy: An interface is like a socket standard (USB-C). Any device — phone, laptop, headphones — that implements that standard can plug in, regardless of what's happening internally. The contract is just "you must expose this shape," not how you work inside.

Practical Exercise

Design an interface Drivable with a method drive(), then create an abstract class Vehicle implementing it partially, and a concrete subclass Car that finishes the job.

public interface Drivable { void drive(); }

public abstract class Vehicle implements Drivable {
    public void startEngine() { System.out.println("Engine on"); }
}

public class Car extends Vehicle {
    @Override
    public void drive() { System.out.println("Car is driving"); }
}

Key Takeaways

  • Abstract classes mix shared implementation with forced-to-implement methods.
  • Interfaces define pure contracts and support multiple implementation.
  • Neither abstract classes nor interfaces can be instantiated directly.
  • Choose abstract class for shared state/code; interface for a capability contract.

Mastery — Design Thinking with OOP

Mastery · ~45 min

The Four Pillars, Working Together

Real Java systems rarely use encapsulation, inheritance, abstraction, and polymorphism in isolation — they combine to keep code flexible and maintainable. Consider a small payroll system that must support many employee types without constantly rewriting logic.

abstract class Employee {
    protected String name;
    public abstract double calculateSalary();
}
class Manager extends Employee {
    @Override
    public double calculateSalary() { return 90000; }
}
class Developer extends Employee {
    @Override
    public double calculateSalary() { return 75000; }
}

// One loop, many behaviors — polymorphism in action:
for (Employee e : allEmployees) {
    System.out.println(e.calculateSalary());
}

Composition Over Inheritance

Inheritance isn't always the right tool. If the relationship is "has-a" rather than "is-a," prefer composition — building a class out of other objects — since deep inheritance chains become rigid and fragile.

// Instead of: class ElectricCar extends Car extends Engine (fragile chain)
class Car {
    private Engine engine;  // composition: Car "has-a" Engine
    public Car(Engine engine) { this.engine = engine; }
    public void start() { engine.ignite(); }
}
Analogy: Composition is like building a computer from separate parts (CPU, RAM, GPU) that you can swap independently, rather than soldering everything into one rigid block. Inheritance chains, if too deep, are closer to that soldered block — hard to change one piece without affecting the rest.

A Glimpse at SOLID: Single Responsibility & Open/Closed

  • Single Responsibility Principle: a class should have one reason to change. A PayrollCalculator shouldn't also handle emailing payslips.
  • Open/Closed Principle: classes should be open for extension (via new subclasses) but closed for modification (you shouldn't have to edit existing tested code just to add a new employee type).

Notice how the Employee hierarchy above already follows Open/Closed: adding an Intern subclass requires zero changes to the payroll loop.

Diagram: Composition vs. Inheritance

Common Misconception: "More inheritance = better OOP design." Deep, unnecessary inheritance hierarchies are a well-known code smell. Senior engineers often deliberately favor composition, reserving inheritance for genuine, stable "is-a" relationships.

Practical Exercise

Refactor a rigid FlyingCar extends Car, Plane (which Java doesn't even allow) into a composition-based design using a FlightModule object.

class FlightModule {
    void takeOff() { System.out.println("Lifting off"); }
}
class FlyingCar extends Car {
    private FlightModule flight = new FlightModule();
    public void fly() { flight.takeOff(); }
}

Key Takeaways

  • The four pillars work together in real systems, not in isolation.
  • Prefer composition ("has-a") over inheritance ("is-a") when the relationship isn't a true hierarchy.
  • Open/Closed Principle: extend behavior with new classes rather than editing existing ones.
  • Good OOP design minimizes future changes to already-tested code.

🏁 Final Practical Challenge

Design a small Library Management system in Java that demonstrates all four pillars:

  • An abstract class LibraryItem with a private title field (encapsulation) and an abstract getLoanPeriodDays() method (abstraction).
  • Two subclasses, Book and DVD, that override getLoanPeriodDays() differently (inheritance + polymorphism).
  • An interface Reservable with a reserve() method, implemented by both subclasses.
  • A Library class that holds a List<LibraryItem> and prints each item's loan period using a single polymorphic loop.
interface Reservable { void reserve(); }

abstract class LibraryItem implements Reservable {
    private String title;
    public LibraryItem(String title) { this.title = title; }
    public abstract int getLoanPeriodDays();
    @Override
    public void reserve() { System.out.println(title + " reserved"); }
}

class Book extends LibraryItem {
    public Book(String t) { super(t); }
    @Override
    public int getLoanPeriodDays() { return 21; }
}
class DVD extends LibraryItem {
    public DVD(String t) { super(t); }
    @Override
    public int getLoanPeriodDays() { return 7; }
}

📝 Summary Notes

Java OOP rests on four pillars: encapsulation (hiding state behind controlled access), inheritance (reusing and extending behavior via "is-a" relationships), polymorphism (one reference type, many runtime behaviors), and abstraction (exposing only what matters through abstract classes and interfaces). Mastery means knowing not just the syntax, but when to reach for inheritance versus composition, and how these pillars combine to keep systems easy to extend without breaking existing code.
